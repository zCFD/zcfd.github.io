.. _boundary_conditions:

Boundary Conditions
-------------------

Boundary conditions are a dict of named blocks nested under the mesh's model
entry, at ``model.<mesh_name>.boundary_conditions``. Each block is keyed by
an arbitrary name (conventionally ``BC_1``, ``BC_2``, ...) and is itself a
dict describing one boundary condition.

.. code-block:: python

    parameters = {
        "config_version": 2,
        "solver": {...},
        "model": {
            "naca0012": {
                "mesh": "naca0012_0449.h5",
                "boundary_conditions": {
                    "BC_1": {"zones": [2, 3], "type": "symmetry"},
                    "BC_2": {"zones": [4], "type": "wall", "kind": "no slip"},
                    "BC_3": {
                        "zones": [1],
                        "type": "farfield",
                        "condition": "IC_1",
                        "kind": "riemann",
                    },
                },
            }
        },
    }

Every boundary condition block requires a **type** (which BC kernel handles
these zones) and **zones** (which mesh zones it applies to). Most types also
require a **kind**, which selects between variants of that type with their
own extra fields — for example a wall's ``kind`` chooses between ``slip``,
``no slip`` and ``wall function``; the fields available below ``kind``
change with the choice.

zCFD supports the following boundary condition types:

.. list-table::
   :widths: 20 80
   :header-rows: 1

   * - BC Type
     - Description
   * - :ref:`Wall <wall>`
     - Wall boundaries
   * - :ref:`Farfield <bc_farfield>`
     - Farfield boundaries with automatic inflow/outflow detection
   * - :ref:`Inflow <bc_inflow>`
     - Pressure, condition-driven or massflow inflow boundaries
   * - :ref:`Outflow <bc_outflow>`
     - Pressure, massflow or radial-pressure-gradient outflow boundaries
   * - :ref:`Mass Flow <bc_mass_flow>`
     - Standalone mass-flow boundary condition
   * - :ref:`Symmetry <bc_symmetry>`
     - Mirror boundary condition
   * - :ref:`Interface <bc_interface>`
     - A boundary joined to another part of the domain: an overset mesh boundary, a sliding interface between two meshes, or one side of a periodic pair


Zones
^^^^^

Every boundary condition block requires a **zones** keyword: a list of
integer zone IDs from the mesh that this BC applies to. The exact zone
numbering is determined by the mesh format and mesh generation tool used —
inspect the mesh (for example with the tool that generated it) to determine
which zone numbers correspond to which physical boundary.

.. list-table::
   :widths: 25 10 10 20 30
   :header-rows: 1

   * - Keyword
     - Required
     - Default
     - Valid values
     - Description
   * - ``zones``
     - Yes
     -
     - List of integers
     - Mesh zone IDs this boundary condition applies to


.. _wall:

Wall
====

Wall boundaries in zCFD can be either slip walls, no-slip walls, or use
automatic wall functions. No-slip walls are appropriate when the mesh is
able to fully resolve the boundary layer (i.e. :math:`y^{+} \leq 1`),
otherwise automatic wall functions should be used. This behaviour is chosen
by setting :code:`'kind'` in the wall specification below. Optionally it is
possible to set wall velocity, roughness, temperature and an FSI modal
model.

:code:`'type'` allows you to choose between a standard :code:`'wall'`
definition or :code:`'immersed wall'` boundaries. Immersed wall boundaries
are *only* supported with meshes created using the :ref:`zM3 <zm3>` mesh
generator. The zM3 mesh generator will determine vectors to represent the
underlying geometry within the 3D Cartesian mesh. It will also generate
additional information such as locations where data is to be sampled in
order to define conditions at the geometry surface, and the subsequent halo
boundary values.

.. note::

    If :code:`'slip'` conditions are chosen, there will be zero momentum
    normal to the wall.

    If :code:`'no slip'` conditions are chosen, the no-slip condition is
    applied directly (mesh must resolve down to :math:`y^{+} \sim 1`). For an
    immersed wall, values computed near the wall are linearly extrapolated
    from the donor (sample) point location associated with that point — this
    can potentially cause sensitivity and early flow separation in strong
    pressure gradients, alleviated to some extent with mesh refinement at
    additional computational cost.

    If :code:`'wall function'` conditions are chosen, any values computed
    near the wall will be based on the Musker wall model, which closely
    represents the flow along a flat plate in zero pressure gradient. As
    such, there are fundamental limitations on the accuracy of this model
    with highly curved surfaces and strong pressure gradients, alleviated to
    some extent with mesh refinement at additional computational cost.


.. list-table::
   :widths: 25 10 10 20 30
   :header-rows: 1

   * - Keyword
     - Required
     - Default
     - Valid values
     - Description
   * - ``zones``
     - Yes
     -
     - List of integers
     - Mesh zone IDs this boundary condition applies to
   * - ``type``
     - Yes
     -

   * - ``kind``

     - Specifies the wall model. slip - zero-normal-momentum wall. no slip - viscous wall requiring :math:`y^+ \sim 1` mesh resolution. wall function - viscous wall with automatic handling of mesh resolution between :math:`y^+ \sim 1` and :math:`y^+ > 100`
   * - ``immersed_wall_normal_type``

   * - ``roughness``

.. _bc_roughness:

Roughness
^^^^^^^^^

.. list-table::
   :widths: 25 10 10 20 30
   :header-rows: 1

   * - Keyword
     - Required
     - Default
     - Valid values
     - Description
   * - ``type``
     - Yes
     -
     - ``'height'`` or ``'length'``
     - How the roughness magnitude is being specified
   * - ``scalar``
     - No (one of ``scalar``/``field`` required)
     -
     - Positive float
     - Value of roughness length or height, in mesh units
   * - ``field``
     - No (one of ``scalar``/``field`` required)
     -
     - Valid filename
     - Name of a VTP file containing a node array called ``Roughness``, used to set the value by nearest-point lookup
   * - ``thermal model``
     - No
     - ``'owen thomson'``
     - ``'owen thomson'`` or ``'reynolds analogy'``
     - How roughness affects wall heat transfer. Only accepted on a wall-function wall that also has a ``temperature`` or a ``heat flux``

Exactly one of ``scalar`` or ``field`` must be set — neither both nor
neither is accepted.

Roughness **length** is the height at which the mean velocity profile of the
flow is zero — beyond this distance from the surface, the flow is
considered effectively smooth and the velocity distribution approaches a
logarithmic law.

Roughness **height** is the average height or magnitude of surface
roughness elements on a solid boundary — the scale of irregularities or
protrusions on the surface that disrupt the smooth flow and create
additional drag or turbulence.

Internally the models work in equivalent sand-grain **height**, so a
``length`` is converted on input as ``height = length / 0.03``. The
``roughness`` surface output variable reports that height, not the value as
written in the deck.

Roughness is applied by the wall-function wall treatment of both the
compressible and the incompressible solver, for the Menter SST and SA-neg
turbulence models.

Example:

.. code-block:: python

    parameters["model"]["background"]["boundary_conditions"]["BC_3"]["roughness"] = {
        "type": "height",
        "scalar": 0.001,
    }


.. _bc_wallfunction:

Wall Function
^^^^^^^^^^^^^

By default a ``'wall function'`` wall uses an incompressible law of the wall:
the velocity profile is solved with the density and viscosity of the first
cell off the wall, and no heat is transferred. Giving the wall a
``temperature`` or a ``heat flux`` switches that wall to the compressible wall
function: the Van Driest II / White-Christoph velocity transformation coupled
to the Crocco-Busemann thermal law of the wall, which evaluates :math:`y^+`
and the wall shear stress with the wall-state density and viscosity and
produces the wall heat flux.

With a ``heat flux`` the wall temperature is recovered; with a ``temperature``
the heat flux is. Both are available as the ``heatflux`` and ``twall`` surface
output variables.

The velocity transformation is worth having at speed whether or not the wall
exchanges heat: the boundary layer of an adiabatic wall is still stratified by
viscous heating. Setting ``compressible wall function`` runs it on an adiabatic
wall, with the wall state evaluated at the recovery temperature :math:`T_r`
rather than at a specified one, so the wall heat flux is zero by construction:

.. code-block:: python

    "BC_2": {
        "zones": [2],
        "type": "wall",
        "kind": "wall function",
        "compressible wall function": True,
    },

``twall`` then reports :math:`T_r` and ``heatflux`` reports zero. The key is
redundant alongside a ``temperature`` or a ``heat flux``, which select the same
transformation and add the thermal closure to it.

A constant-heat-flux wall is singular where the boundary layer is thin, for
example at a plate leading edge: the modelled layer cannot carry an arbitrarily
large flux there and the wall temperature will rise until it is limited
internally. Check the ``twall`` output if a prescribed flux is large.

The compressible wall function, however it is selected, is not supported on
immersed walls or in the incompressible solver, and these combinations are
rejected at input validation.

.. _bc_rough_compressible_wallfunction:

Rough compressible walls
""""""""""""""""""""""""

:ref:`Roughness <bc_roughness>` may be combined with the compressible wall
function. This is the combination an icing calculation needs: ice accretion
roughens the surface, which raises both the skin friction and the convective
heat transfer that in turn drives the accretion, while an ice protection system
imposes a wall ``heat flux`` or ``temperature``. Both the roughness and the
thermal state accept a ``field``, so an ice roughness map and an electrothermal
pad layout can be prescribed per face from VTP files.

The equivalent sand-grain height is given in **mesh units**, like every other
length in the input deck — nothing rescales the mesh, so a 0.5 mm ice roughness
on a metre-scale mesh is ``0.0005``.

On the velocity side the Van Driest transformed velocity obeys the
incompressible rough-wall law, with the roughness Reynolds number
:math:`k_s^+` formed from the **wall** density and viscosity rather than those
of the first cell. That is the same scaling the compressible wall function
already uses for :math:`y^+` and the wall shear stress; on a heated anti-iced
wall the two differ substantially.

On the thermal side the Crocco-Busemann closure is an exact Reynolds analogy,
so on its own it would raise the Stanton number in the same ratio as the skin
friction. Roughness elements shed momentum by pressure drag but carry heat only
by conduction, so in reality the heat transfer rises much less. The default
``thermal model`` of ``'owen thomson'`` therefore adds a thermal sublayer
resistance

.. math::

    \Delta T^+ = 0.52 \, (k_s^+)^{0.45} \, Pr^{0.8}

between the surface and the roughness crest, blended in over the same
:math:`k_s^+` range as the velocity intercept so a hydraulically smooth wall is
unaffected. Setting ``thermal model`` to ``'reynolds analogy'`` removes it.

With a rough wall the ``twall`` output is the temperature of the **surface**,
not of the roughness crest the law of the wall is closed on; the two differ by
the drop across that resistance. ``heatflux`` is continuous through it and so
is unambiguous.

Example — an anti-iced leading edge with a measured ice roughness map:

.. code-block:: python

    parameters["model"]["background"]["boundary_conditions"]["BC_3"] = {
        "type": "wall",
        "kind": "wall function",
        "heat flux": {"field": "ips_pads.vtp"},
        "roughness": {"type": "height", "field": "ice_roughness.vtp"},
    }

.. _bc_velocity:

Velocity
^^^^^^^^

The ``velocity`` keyword applies a surface velocity, used to model cases
with surfaces in relative motion, e.g. a car moving over a road surface or a
rotating tyre. The wall boundary condition supports either a **linear**
velocity or a **rotating** one, selected by its own ``type`` field.

The options for the **linear** velocity are:

.. list-table::
   :widths: 25 10 10 20 30
   :header-rows: 1

   * - Keyword
     - Required
     - Default
     - Valid values
     - Description
   * - ``type``
     - Yes
     -
     - ``'linear'``
     - Selects a linear (translational) wall velocity
   * - ``vector``
     - Yes
     -
     - ``[x, y, z]``
     - Direction of the translation velocity
   * - ``mach``
     - No
     -
     - Number
     - Overrides the magnitude of the translation velocity vector

The options for the **rotating** velocity are:

.. list-table::
   :widths: 25 10 10 20 30
   :header-rows: 1

   * - Keyword
     - Required
     - Default
     - Valid values
     - Description
   * - ``type``
     - Yes
     -
     - ``'rotating'``
     - Selects a rotational wall velocity
   * - ``axis``
     - Yes
     -
     - ``[x, y, z]``: unit vector
     - Axis of rotation
   * - ``center``
     - Yes
     -
     - ``[x, y, z]``
     - Origin (centre point) of the rotation axis
   * - ``omega``
     - Yes
     -
     - Number
     - Angular velocity of the rotation, in radians per second

Example linear wall velocity:

.. code-block:: python

.. _bc_temperature:

Temperature
^^^^^^^^^^^

A wall is adiabatic unless it is given a ``temperature`` or, on a
``'wall function'`` wall, a ``heat flux``. Both take the same value: a number
for a uniform wall, or a dictionary with a single ``field`` key naming a VTP
file for a value that varies over the wall. The file must carry a point array
named ``Temperature`` (Kelvin) or ``HeatFlux`` (W/m\ :sup:`2`), and each wall
face takes the value at the nearest point, or the interpolated value when the
file carries cells. Heat flux is **positive into the fluid**, i.e. a heated
wall; negative values remove energy.

.. list-table::
   :widths: 25 10 10 20 30
   :header-rows: 1

   * - Keyword
     - Required
     - Default
     - Valid values
     - Description
   * - ``temperature``
     - No
     - unset (adiabatic)
     - Number (Kelvin) or ``{"field": "<file>.vtp"}``
     - Wall temperature
   * - ``heat flux``
     - No
     - unset (adiabatic)
     - Number (W/m\ :sup:`2`) or ``{"field": "<file>.vtp"}``
     - Prescribed wall heat flux. ``'wall function'`` walls only; mutually exclusive with ``temperature``

Examples:

.. code-block:: python

    "BC_1": {"zones": [1], "type": "wall", "kind": "no slip", "temperature": 310.0},
    "BC_2": {"zones": [2], "type": "wall", "kind": "wall function", "temperature": 290.0},
    "BC_3": {"zones": [3], "type": "wall", "kind": "wall function", "heat flux": 5.0e3},
    "BC_4": {"zones": [4], "type": "wall", "kind": "no slip", "temperature": {"field": "hot_patch.vtp"}},

.. _bc_wall_fsi:

FSI
^^^

The ``fsi`` keyword attaches a fluid-structure-interaction modal model to a
wall boundary (any ``kind``), coupling the wall's motion to a structural
solve. The full set of FSI model parameters is documented separately in
:ref:`Fluid-structure interaction <fsi>`; this section only shows how it
attaches to a wall BC.

Example:

.. code-block:: python

    "BC_FSI": {
        "zones": fsi_zones,
        "type": "wall",
        "kind": "slip",
        "fsi": {
            "type": "modal_model",
            "file_format": "nastran",
            "nastran_casename": "panel_nm_0.04m",
            "transform_type": "rbf_multiscale",
            "base_point_fraction": 1.0,
            "support_radius": 0.02,
            "scale": [1.0, 1.0, 1.0],
            "mode_mapping_max_distance": 0.01,
            "fluid_force_scaling": 0.08 / 0.000166667,
            "mode_list": [0, 4, 10, 13],
            "modal_damping": [0.0, 0.0, 0.0, 0.0],
        },
    },


.. _bc_farfield:

Farfield
========

Farfield boundary conditions are typically used for external flow
simulations and automatically switch between inflow and outflow. This
boundary condition cannot be used with the incompressible solver. The
farfield boundary automatically determines whether the flow is locally an
inflow or an outflow by solving a Riemann equation (for ``kind: 'riemann'``
and ``'preconditioned'``). The conditions on the farfield boundary are set
by referring to a :ref:`reference condition <reference_conditions>` block.

.. list-table::
   :widths: 20 10 10 20 35
   :header-rows: 1

   * - Keyword
     - Required
     - Default
     - Valid values
     - Description
   * - ``zones``
     - Yes
     -
     - List of integers
     - Mesh zone IDs this boundary condition applies to
   * - ``type``
     - Yes
     -
     - ``'farfield'``
     - Boundary condition type
   * - ``kind``
     - No
     - ``'riemann'``
     - ``'riemann'``, ``'pressure'``, ``'supersonic'`` or ``'preconditioned'``
     - Model used for the farfield boundary:
            * *riemann* uses Riemann invariants for a non-reflecting inflow with a pressure outflow.
            * *pressure* uses a pressure boundary condition for both inflow (downstream pressure) and outflow (user-specified pressure).
            * *supersonic* uses upstream conditions for both inflow and outflow.
            * *preconditioned* is a preconditioned variant of the Riemann boundary condition.
   * - ``condition``
     - Yes
     -
     - String reference to a reference condition
     - Reference flow condition block for these boundaries — see :ref:`reference conditions <reference_conditions>`
   * - ``sponge_layer_damping``
     - No
     -
     - See :ref:`Sponge Layer Damping <bc_sponge_layer_damping>`
     - Optional sponge layer damping applied near this boundary
   * - ``driver``
     - No
     -
     - See :ref:`Force Driver <bc_force_driver>`
     - Optional automatic driver that adjusts the inflow to target a force coefficient

Example farfield with ``kind: 'riemann'``:

.. code-block:: python

    "BC_3": {"zones": [1], "type": "farfield", "condition": "IC_1", "kind": "riemann"},

Example farfield with ``kind: 'pressure'``:

.. code-block:: python

    parameters["model"]["naca0012"]["boundary_conditions"]["BC_3"] = {
        "zones": [1],
        "type": "farfield",
        "condition": "IC_2",
        "kind": "pressure",
    }

``kind: 'supersonic'`` and ``kind: 'preconditioned'`` are valid schema values
but no current testcase exercises either — both are constructed the same
way, just with ``"kind": "supersonic"`` or ``"kind": "preconditioned"``
substituted above.

.. _bc_force_driver:

Force Driver
^^^^^^^^^^^^

Drives a farfield boundary's inflow conditions to target a specific force
coefficient by adjusting a control variable (angle of attack or velocity
magnitude). Declare *what* you want (target, value, control mode); the
runtime controller handles the feedback loop.

.. list-table::
   :widths: 25 10 10 20 30
   :header-rows: 1

   * - Keyword
     - Required
     - Default
     - Valid values
     - Description
   * - ``target``
     - Yes
     -
     - String
     - Report column name to target (e.g. ``'wall_Ftz'``)
   * - ``target_value``
     - Yes
     -
     - Number
     - Target value for the force component
   * - ``force_report``
     - Yes
     -
     - String
     - Name of the force report block (e.g. ``'FR_1'``) to read forces from
   * - ``control``
     - Yes
     -
     - ``'angle_of_attack'`` or ``'velocity_magnitude'``
     - Control variable to adjust
   * - ``initial_value``
     - No
     - 0.0
     - Number
     - Starting value for the control variable (AoA: degrees, velocity: Mach)
   * - ``max_increment``
     - No
     - 2.0
     - Number > 0
     - Maximum change per update
   * - ``relaxation_factor``
     - No
     - 0.75
     - 0 < Number <= 2.0
     - Under-relaxation factor for updates
   * - ``update_period``
     - No
     - 200
     - Integer > 0
     - Cycles between control variable updates
   * - ``settling_period``
     - No
     - 500
     - Integer >= 0
     - Initial cycles before the first update
   * - ``convergence_tolerance``
     - No
     - 1.0e-4
     - Number > 0
     - Target error tolerance for convergence
   * - ``smoothing_window``
     - No
     - 20
     - Integer > 0
     - Moving-average window for force smoothing

Example:

.. code-block:: python

    parameters["model"]["naca0012"]["boundary_conditions"]["BC_3"] = {
        "zones": [2, 3, 5],
        "type": "farfield",
        "condition": "IC_2",
        "kind": "riemann",
        "driver": {
            "target": "wall_Ftz",
            "target_value": 1.0778,
            "force_report": "FR_1",
            "control": "angle_of_attack",
        },
    }

.. note::

    The native ``driver`` block validates and registers correctly, but the
    angle-of-attack control mode does not engage at runtime for at least one
    known case: it reports zero update every cycle instead of converging
    alpha onto the target. This is a known solver-wiring gap, not a
    documentation error — do not rely on ``driver`` for angle-of-attack
    control until it is fixed.


.. _bc_inflow:

Inflow
======

zCFD supports three kinds of inflow boundary condition, selected using the
:code:`'kind'` key: ``'default'``, ``'pressure'`` and ``'massflow'``. All
three refer to a :ref:`reference condition <reference_conditions>` via the
``reference`` keyword (**not** ``condition`` — that keyword is farfield's).
By default the flow direction is normal to the boundary; the ``'pressure'``
kind can override this with an explicit direction vector.

.. note::

    The massflow rate needs to be specified in kg/s and can only be used if
    the mesh is in metres. Massflow ratio is nondimensional, where
    :math:`A_{in}` is defined in mesh units:
    :math:`massflowratio = \rho_{in} U_{in} A_{in}/(\rho_{ref} U_{ref})`.

Common fields:

.. list-table::
   :widths: 20 10 10 20 35
   :header-rows: 1

   * - Keyword
     - Required
     - Default
     - Valid values
     - Description
   * - ``zones``
     - Yes
     -
     - List of integers
     - Mesh zone IDs this boundary condition applies to
   * - ``type``
     - Yes
     -
     - ``'inflow'``
     - Boundary condition type
   * - ``kind``
     - No
     - ``'default'``
     - ``'default'``, ``'pressure'`` or ``'massflow'``
     - Selects how the inflow state is specified
   * - ``reference``
     - No (required in practice — see kinds below)
     -
     - String reference to a reference condition
     - Reference condition supplying the base state for ratio fields

``kind: 'default'`` (condition-driven inflow — the incompressible solver's
velocity inlet; carries no extra fields beyond the common ones above):

Example:

.. code-block:: python

    "BC_3": {"zones": [1], "type": "inflow", "kind": "default", "reference": "IC_1"},

``kind: 'pressure'`` — velocity and density are derived from a total
pressure ratio and total temperature ratio relative to ``reference``:

.. list-table::

.. _bc_interface:

Interface
=========

An interface boundary condition (``type: 'interface'``) joins a boundary to
another part of the domain rather than closing it off: the solution on one
side is supplied by the other. The ``kind`` selects how the two sides are
joined:

* ``'overset'`` — this mesh overlaps another, and takes the values in its
  fringe from the mesh beneath it.
* ``'sliding'`` — two meshes meet on a shared surface of revolution with
  non-matching faces, and exchange a conservative flux across it.
* ``'periodic'`` — two boundaries of the same mesh are treated as one
  surface, related by a rotation or a translation.

Every interface names what it connects to in its ``connection`` block. What
the connection holds depends on the ``kind``, and is described in each
subsection below.

.. _bc_overset:

Overset
^^^^^^^

The overset interface is applied to the outer boundaries of a mesh that is
overset on top of one or more other meshes. See :ref:`Overset <overset>` for
how an overset case is set up and solved.

   :widths: 20 10 10 20 35
   :header-rows: 1

     - Valid values
     - Description
   * - ``zones``

     -
     - List of integers
     - Mesh zone IDs this boundary condition applies to
   * - ``type``

     - Boundary condition type

     - ``'overset'``
     - Interface kind

     - unset (maps against every preceding model)
     - See below
     - The model(s) whose mesh provides donor data at this interface
   * - ``interpolation_method``

     - ``least-squares``

     - Donor interpolation method: ``nearest cell`` the containing cell's value, ``inverse distance`` a distance-weighted average, ``green-gauss`` a Green-Gauss reconstruction, ``least-squares`` a least-squares reconstruction
   * - ``additional_active_layers``

topologically sorted so that a model always appears after the model(s) it

        "type": "interface",
        "kind": "overset",
        "connection": {"model": ["background"]},
    },

.. _bc_sliding:

Sliding
^^^^^^^

A sliding interface joins two models whose meshes abut, without
overlapping, on a shared cylindrical, conical or annular surface — typically
a rotating region and the stationary region around it. The faces on the two
sides need not match. The two face sets are clipped against each other into
a common set of intersection polygons, one numerical flux is computed per
polygon, and that flux is applied to the cell on each side, so the interface
is conservative rather than interpolated.

A sliding interface is declared on both models, and each names the other.
The connection gives the model and the boundary on the other side; that
boundary must itself be a sliding interface whose connection names this one
back.

The interface must be a surface of revolution about the axis of the rotating
fluid zone on either side. When neither side rotates, the two meshes are
simply joined, and the axis is found from the shape of the interface itself.

The interface may be a cylinder, a cone, a flat annulus, a spherical band, a
disc or spherical cap that reaches the axis, or a whole sphere centred on the
axis. It must cover the full circle about the axis; a periodic sector is not
supported. The summary printed at the start of the run names the shape the
solver found, which is a quick check that the right zones were listed.

A closed or compound surface, such as a drum's two faces and its side, can be
declared either way:

* as one sliding interface on each side that lists every zone. The solver
  groups the zones into single surfaces, a cylinder meshed as two zones
  counting as one, and pairs each surface with the matching one on the other
  side;
* as one sliding interface per surface, each naming its partner, when the
  pairing should be stated explicitly.

A zone that matches no surface on the other side stops the run at setup, with
the zone, the model and the shape it was found to have.

.. code-block:: python

    "outer": {"boundary conditions": {
        "BC_2": {"zones": [10, 63, 62], "type": "interface", "kind": "sliding",
                 "connection": {"model": "disc", "boundary": "BC_1"}}}},
    "disc": {"boundary conditions": {
        "BC_1": {"zones": [21, 22, 23], "type": "interface", "kind": "sliding",
                 "connection": {"model": "outer", "boundary": "BC_2"}}}},

   :widths: 20 10 10 20 35
   :header-rows: 1

   * - Keyword
     - Required
     - Default
     - Valid values
     - Description
   * - ``zones``
     - Yes
     -
     - List of integers
     - Mesh zone IDs this boundary condition applies to
   * - ``type``
     - Yes
     -
     - ``'interface'``
     - Boundary condition type
   * - ``kind``
     - Yes
     -

     - Interface kind

The options for the sliding ``connection`` are:

.. list-table::
   :widths: 25 10 10 20 30
   :header-rows: 1

   * - Keyword
     - Required
     - Default
     - Valid values
     - Description
   * - ``model``
     - Yes
     -
     - Model name
     - The model on the other side of this interface. It must be another model in the case
   * - ``boundary``
     - Yes
     -
     - Boundary condition name
     - The boundary condition on that model that forms the other side of this interface

``area``
    ``conservative`` gives both sides the mean of the two parent area maps,
    so the interface conserves to round-off and the per-face closure error
    is first order in cell width. ``free stream`` gives each side its own
    parent map, so closure, and with it free-stream preservation, is exact
    and the conservation deficit is second order. The two are identical on
    a planar interface and for matching meshes.

``flux``
    ``segment`` computes one flux per intersection polygon, applied with a
    shared area vector to the cell on each side, so the two sides cancel
    exactly and the interface conserves. ``parent`` computes one flux per
    parent face instead, against the area-weighted average of that face's
    donors and with the parent face's own area vector. The flux then does not
    change when the intersection pattern changes, so the noise a rotating
    interface makes as cells pass one another is lower, but each side fluxes
    its own faces and nothing cancels: the interface is not conservative.
    ``segment`` is the default for that reason.

The following advanced options are rarely needed:

.. list-table::
   :widths: 25 10 10 20 30
   :header-rows: 1

   * - Keyword
     - Required
     - Default
     - Valid values
     - Description
   * - ``segment_capacity_factor``
     - No
     - 8
     - Integer >= 1
     - Segment storage reserved per interface face. The intersection is rebuilt every real time step and its segment count varies with the rotation angle, so storage is reserved once at this multiple of the local interface face count. Setup sweeps a full revolution and stops with the factor actually needed if this is too small
   * - ``sliver_tolerance``
     - No
     - 1.0e-10
     - Number >= 0
     - Overlaps smaller than this fraction of the smaller parent face are discarded. Slivers carry no useful flux but each costs a segment slot
   * - ``closure_tolerance``
     - No
     - 1.0e-2
     - Number >= 0
     - Largest fraction of a face's area that may be left uncovered by its segments before setup stops. A real gap between the two sides (mismatched radii, a partial annulus, a wrong axis) shows up here rather than as a silent leak

                    "type": "interface",
                    "kind": "sliding",
                    "connection": {"model": "stator", "boundary": "BC_2"},
                },
            },
        },
        "stator": {
            "mesh": "stator.h5",
            "boundary_conditions": {
                "BC_2": {
                    "zones": [20],
                    "type": "interface",
                    "kind": "sliding",
                    "connection": {"model": "rotor", "boundary": "BC_3"},
                },
            },
        },
    },

.. _bc_periodic:

Periodic
^^^^^^^^

A periodic interface treats two boundaries of the same mesh as one surface,
with the flow leaving one boundary entering the other. It is specified in
pairs: each boundary's connection names the other boundary of the pair, and
that boundary must name this one back.

Each side carries the ``transform`` that maps it onto the other side, so the
two transforms must be inverses of each other. A rotation of theta about an
axis pairs with a rotation of -theta about the same axis line (equivalently,
theta about the reversed axis); a translation by a vector pairs with the
translation by its negative. Both sides of a pair use the same transform
``type``.

.. note::

    The incompressible solver (``solver_settings.type: 'incompressible'``)
    only supports the **'linear'** (translational) periodic transform.
    **'rotated'** periodic interfaces are only supported by the
    compressible solver.
